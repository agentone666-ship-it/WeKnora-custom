WEKNORA · WIKI PIPELINE

Wiki 是怎么被
“抽”出来的？

这份页面根据 WeKnora 源码梳理概念抽取、页面生成、页面连接和置信度的实际机制。

一句话结论：它不是纯靠 LLM，也不是纯固定算法，而是固定 SOP 编排多个 LLM 语义判断，再用确定性代码校验、落库和维护关系的混合系统。

先看懂这些技术名词

先用一份介绍“腾讯用 RAG 建知识库”的文档举例。系统读完后，可能抽出“腾讯”和“RAG”两个 Wiki 页面。

Entity（实体）

现实中可以明确指出来的具体对象。例如一个人、公司、产品、地点或事件。“腾讯”“马化腾”“微信”都属于 Entity。可以把它理解为 Wiki 中的“具体名词”。

Concept（概念）

抽象的知识、方法、理论或主题。例如“RAG”“机器学习”“向量检索”。它不是某一家具体公司，而是一种可以被解释的方法或思想。

Summary（摘要页）

一份原始文档的内容简介。Entity 和 Concept 是围绕某个对象组织知识；Summary 则回答“这整份文档讲了什么”。

Slug（页面唯一名）

系统给页面使用的稳定地址和唯一标识。类似人的身份证号或网页路径。例如“腾讯”的标题可以改变，但 slug 可能一直是 entity/tencent，链接靠它找到正确页面。

Alias（别名）

同一个对象的其他叫法。例如“腾讯控股”“Tencent”可以是“腾讯”的 Alias。正文命中别名时，也可能自动连接到同一个 Wiki 页面。

Chunk（文档切片）

把长文档切成的小段文字。就像把一本书拆成许多带编号的段落。这样系统能指出某条 Wiki 内容具体来自哪一段，而不是只说“来自这本书”。

Citation（引用 / 证据）

某条内容所依据的原文位置。当系统说一个 Chunk 支持“RAG”页面，就是在建立证据关系，方便追溯这句话从哪里来。

SourceRefs / ChunkRefs

页面保存的来源清单。SourceRefs 指向哪几份原始文档；ChunkRefs 更精确，指向文档中的哪些切片。

InLinks / OutLinks

页面之间的来往连接。A 页面链接 B，A 就有一条 OutLink（出链）；B 会记录一条来自 A 的 InLink（入链）。

Embedding（向量表示）

把文字转换成一串数字，让计算机比较语义是否接近。在这里主要用于筛选可能合适的目录，不会直接决定两个 Wiki 页面必须连接。

Reduce（汇总合并阶段）

把不同文档抽出的同一主题合并成一个页面。例如三份文档都提到腾讯，系统会更新同一个腾讯页面，而不是简单生成三份重复页面。

Fallback（兜底方案）

主要步骤失败时采用的备用内容。如果没有找到具体证据 Chunk，系统仍可能用候选抽取阶段生成的简短描述来创建页面。

把它串起来：长文档被切成 Chunk → LLM 从中识别具体的 Entity 和抽象的 Concept → 每个页面获得稳定的 Slug → 页面用 SourceRefs / ChunkRefs 记录证据 → 页面之间通过 OutLinks / InLinks 形成网络。

完整生成流程

固定规则文档与 Chunk读取切片、重建正文、截断，并拦截无有效文本的文档。
→
LLM候选抽取识别重要 Entity / Concept，生成名称、别名、描述和 slug。
→
LLM证据分类判断哪些 Chunk 实质支持每个候选，也允许补充遗漏候选。
→
混合页面合并代码组织证据，LLM 更新正文、处理冲突与撤回。
→
混合目录与连接目录候选向量预筛；LLM 分类；规则补链、清理死链。

抽出了哪些 Wiki 页面？

Summary

规则 + LLM

每份原始文档对应一个摘要页。正文由 LLM 概括，但 slug 按 Knowledge ID 确定生成：summary/<id>。

Entity

LLM 判断

人物、组织、产品、地点、技术、事件等具体对象，slug 采用 entity/*。

Concept

LLM 判断

主题、方法论、理论和抽象概念，slug 采用 concept/*。

LLM 决定“什么值得成为页面”，但 Prompt 和代码固定了边界：不能把简单提及提升成页面；Entity 与 Concept 不得重复；更新文档时应复用旧 slug；输出必须满足 JSON 和类型格式。

页面正文如何形成？

证据优先

引用分类阶段把候选关联到具体 Chunk。页面保存原始文档级 SourceRefs 和切片级 ChunkRefs。

增量编辑

已有页面不会简单覆盖。LLM 接收旧正文、新证据、删除来源及仍有效来源，然后执行添加、合并、冲突说明和撤回。

固定约束

新增事实要求引用；不得发明证据外信息；信息必须属于当前主题；链接只能使用合法 slug 白名单。

Wiki 与 Wiki 为什么会连接？

这里最关键的理解：WeKnora 当前建立的不是“实体关系图谱”，而是“Wiki 页面引用网络”。它不会专门产出“腾讯—开发了→微信”或“RAG—依赖→向量检索”这样的关系类型；它表达的只是：A 页正文提到了 B 页代表的对象，所以 A 页链接到 B 页。

真正的语义连接条件

条件 1：B 已经是候选 Wiki

B 必须先被抽取为 Entity 或 Concept，或者本来就是已有页面。只在正文中出现、但没有被抽成 Wiki 的普通词，不会有目标页面可连。

条件 2：A 的正文确实提到 B

A 页生成后的正文里必须出现 B 的标题或 Alias。例如“腾讯”页正文写到“微信”，并且“微信”已有 Wiki 页，才具备建立连接的条件。

条件 3：B 在允许候选范围内

系统不会拿整个知识库所有页面做全局语义判断。候选主要来自本批新写入的兄弟页面，以及 A 已有的出链目标；因此历史页面可能漏连。

用具体例子理解

文档或页面内容是否连接为什么
“腾讯推出了微信。”且腾讯、微信都已抽成 Entity会连接腾讯页面正文出现“微信”，系统建立“腾讯页引用微信页”的边；但边本身不保存“推出了”这个关系类型。
“RAG 通常结合向量检索。”且两者都已抽成 Concept会连接RAG 页面正文出现“向量检索”，形成普通引用边；不会标记为“依赖关系”。
同一份文档分别提到腾讯和阿里，但两者没有出现在彼此页面正文中不一定连接仅仅来自同一份文档、同一目录或同一批次，不足以保证连接；必须有页面正文中的实际提及。
正文提到“数据库”，但“数据库”没有被抽成 Concept 页面不连接没有目标 Wiki 页面和 slug，普通文字不会凭空形成边。
两个页面向量很相似，但正文没有互相提及不连接Embedding/Qdrant 相似度不是建立 Wiki 边的条件。
A 页正文提到 B，但 B 是旧页面且没有进入本轮候选范围可能漏连自动补链为了性能只扫描有限候选，并非全知识库全量实体链接。

两条实际建链路径

摘要页中的 LLM 链接

LLM 写作

系统把本文件抽出的 Wiki 清单交给 LLM。Prompt 要求：摘要中只要提到清单里某个页面的标题或别名，就必须写成 Wiki 链接。因此它仍然是“提到就连”，不是让 LLM 输出关系类别。

页面生成后的规则补链

精确文本规则

系统检查 A 页正文是否出现候选 B 的标题或别名。出现就把第一次安全命中变成链接；它不理解句子里的“属于、开发、竞争、依赖”等谓词。

边表达了什么？

引用关系

边只能可靠表达“A 页面提到了/引用了 B 页面”。真正的业务关系仍留在 A 页正文句子中，没有被结构化到边上。

因此，真正形成图连接的不是 Qdrant 相似度，而是正文里的 Wiki 标记：

当前 Wiki 页面
[[concept/rag|RAG]]→ OutLinks
← InLinks
concept/rag

来源 A：LLM 写入

LLM

摘要中提到合法清单里的页面名称或别名时，Prompt 强制 LLM 链接；不能发明新目标或自链接。

来源 B：自动补链

纯规则

代码扫描候选页面的标题和别名，正文精确命中后，把第一次安全出现转换为 [[slug|原文]]。

最终落边

纯规则

解析 [[...]] 得到 OutLinks，再同步目标页 InLinks。边没有 relation_type、语义标签、权重或置信度。

自动补链还会：优先匹配长名称；每个目标最多补一次；跳过代码块、行内代码、已有链接、Markdown 链接、图片和自链接。死链接则会尝试修复，否则退回普通文本。

LLM 与固定 SOP 的分工

环节执行者实际作用
重要概念识别LLM判断什么值得成为 Entity / Concept
页面 slug 类型与连续性混合LLM 输出，Prompt 与代码限定格式并复用旧 slug

有没有“自信度”？

当前没有正式的页面级、事实级或边级 Confidence

WikiPage、抽取结果和图节点/边中都没有 confidence 字段；Prompt 也不要求 LLM 返回 confidence。因此每个 Wiki 页面和页面连接都没有一个可供展示、排序或发布拦截的正式置信度。

Jaccard Score

只用于去重候选预筛，把可能重复的旧页面交给 LLM 判断；不存进 Wiki。

Cosine Score

只用于挑选可能相关的目录候选；不代表页面可信度或连接强度。

Health Score

衡量整个知识库的孤立页、死链、空页面等健康情况，不是单页 confidence。

ChunkRefs 和 SourceRefs 是证据链，但不是数值置信度。尤其要注意：没有匹配到 Chunk 的候选不会必然淘汰，而可能使用第一阶段生成的 Description / Details 作为 fallback，因此系统目前没有按低置信度阻止页面生成。

如果要补置信度，应该怎么做？

建议：Confidence = 证据 Chunk 覆盖 + 来源文档数量 + 实质提及覆盖率 + 重复抽取稳定性 + 来源质量 − fallback 惩罚
  • 把分数做到事实级，再聚合成页面级，而不是让 LLM 主观报一个数字。
  • 页面连接应区分“LLM 显式链接”和“规则文本命中”，并分别计分。
  • 低分页面可以进入草稿或待审核状态；低分边可以不进入主图展示。
